Parameters and associativity

Understand which values stay editable and which relationships must follow later dimension changes.

The practical question

Suppose a frame is 800 mm wide today, but you expect to change it to 900 mm later. You want two things to happen:

  • the frame geometry becomes wider;
  • parts attached to the right side move with that side.

The first is a parameter problem. The second is an associativity problem. They are related, but they are not the same thing.

Parameter: a value that should remain editable

For a plain Forge model, public lower-case numeric attributes are intended to become editable SolidCraft parameters:

class Frame:
    width = 800.0
    height = 400.0
    wood_thickness = 12.0

Those values are part of the model's design intent. They are different from temporary Python calculations used only while building the command plan.

Make parameter intent visible in the name

Python nameMeaningNative editable parameter?
width = 800.0Design dimensionYes
_panel_pitch = 160.0Forge/build-time helperNo
PANEL_COUNT = 5Fixed constantNo

This naming convention prevents a Python implementation detail from looking like a promise that the value remains editable in the saved CAD design.

Derived dimensions should remain symbolic where possible

Simple arithmetic on parameters can stay symbolic:

class Frame:
    width = 800.0

    def build(self):
        half_width = self.width / 2
        return SideBoard().move(x=half_width)

However, not every Python operation can or should become a CAD expression. If Forge needs a concrete number for Python control flow, it may use pv(). At that moment the value is being evaluated during the Forge run.

A parameter can be accidentally flattened

This is the important trap: geometry may remain parameterized while one placement is calculated only once in Python.

x = pv(self.width) / 2
right = SideBoard().move(x=x)

If the saved SolidCraft parameter later changes, that one-time placement cannot automatically know that it should move too. Forge emits ModelParameterWarning for supported cases where a public parameter is partly flattened in this way.

Rule of thumb: if you expect a relationship to update after editing the saved SolidCraft design, the relationship itself must be represented natively or symbolically. Keeping only the source dimension parametric is not enough.

Associativity: relationships that survive edits

An associative model expresses why geometry belongs somewhere. For example:

block = Block().attach(
    base,
    parent=Anchor.RIGHT,
    child=Anchor.LEFT,
)

If the parent width changes, the semantic RIGHT face should move and the child should follow it. The attachment is therefore more useful than calculating the original right-face X coordinate once.

Parametric relationship values

A relationship value can itself be a parameter:

class Mount:
    gap = 10.0

    def build(self):
        return Block().attach(
            base,
            parent=Anchor.RIGHT,
            child=Anchor.LEFT,
            gap=self.gap,
        )

For supported attachments, Forge keeps the gap as a native joint value. Changing the saved gap parameter can then re-solve the relationship without rerunning Python.

Share one design parameter across components

Several reusable parts may depend on one assembly-level design value. Pass the symbolic parent parameter into those components instead of creating unrelated duplicates:

bottom = BottomBoard(corner_radius=self.corner_radius)
roof = RoofBoard(corner_radius=self.corner_radius)
bracket = CornerBracket(
    inside_corner_radius=self.corner_radius,
)

All three uses express one design decision: the same corner radius.

Not every useful value should be parametric

Some values genuinely belong only to the Forge build process. Examples can include a loop count, an intermediate lookup, a temporary placement used to construct a non-associative reference model or a choice between two source branches.

Use an underscore or constant when the model is intentionally rebuilt from Python after changing that value. Do not pretend every Python number is a native CAD parameter.

How Forge proves associativity

Initial geometry is not enough evidence. A parametric qualification case should:

  1. build and save the native SolidCraft design;
  2. measure the initial result;
  3. change the native parameter with parameters.change;
  4. evaluate the saved design again without rerunning the Python model;
  5. measure that the dependent geometry or attachment moved correctly.

This is qualification level Q5 in the Forge test system.

Example: wood thickness and a bracket

If a bracket must stay aligned when wood_thickness changes, there are two independent questions:

  • does SolidCraft still know the new board geometry?
  • is the bracket relationship expressed in a way that follows that geometry and preserves any intended local correction?

Changing the parameter successfully while the bracket remains frozen is therefore a failed associative use case, even if the board itself updates.
