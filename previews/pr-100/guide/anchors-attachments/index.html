Anchors and attachments

Describe where parts connect, which way they face and which relationship should remain associative.

Why anchors exist

If you place every part with absolute X/Y/Z coordinates, the model may look correct once but becomes fragile as soon as dimensions change. An anchor gives a part a meaningful attachment reference such as “right face”, “front-top-left corner” or a named mounting frame.

The important idea is not the coordinate value itself. The important idea is what place on the part this coordinate represents and, for oriented attachments, which way the local attachment frame points.

An attachment relates two anchors

attach() always describes a relationship between a parent reference and a child reference:

bracket = Bracket().attach(
    frame,
    parent=Anchor.FRONT_TOP_LEFT,
    child=Anchor.BACK_TOP_RIGHT,
)

Read this as:

  • find the parent's front-top-left attachment reference;
  • take the child's back-top-right attachment reference;
  • place the child so those references form the requested relationship.

You should not need to calculate the final world coordinates yourself.

These names describe the part from its own local coordinate system. A corner anchor should continue to mean the same corner when a parameter changes the part's width or height.

An anchor is more than a world point

A reliable attachment needs a local frame. Conceptually that frame contains:

  • an origin — where the attachment is;
  • a normal/direction — which way it faces;
  • a rotation reference around that normal.

This is why the same numeric adjustment can behave differently at different corners if it is interpreted in the anchor's local coordinate system. A local attachment offset is not automatically a world-X, world-Y or world-Z move.

Design rule: Forge should make the coordinate space explicit. The user should never have to guess whether an offset is local to the anchor or global to the assembly.

Gap and offset describe different parts of the relationship

ValueMeaningCoordinate space
gapDistance away from/toward the parent along the attachment normalLocal normal
offset=(u,v)Movement within the attachment planeLocal anchor plane
move(x,y,z)Explicit occurrence translationAssembly/world axes
orientationWhich way the child facesAnchor/component frame

Keeping these concepts separate is important for parametric models. If an offset is local, Forge should preserve it as a local relationship instead of flattening it into one-time global coordinates.

AnchorFrame: define a custom oriented mounting frame

Use AnchorFrame when the attachment location is not one of the standard faces/corners, or when the orientation must be stated explicitly.

mount = AnchorFrame(
    origin=(0, 0, -12),
    z=(0, 1, 0),
    x=(0, 0, -1),
)

Here:

  • origin is the component-local mounting point;
  • z is the local attachment direction;
  • x fixes the rotation around that direction.

This is conceptually close to BOSL2's attachable model: a useful anchor has both a location and local orientation. Forge does not need to copy BOSL2's API, but that mental model is a good check for clear semantics.

AnchorTopology: follow real model topology

Sometimes a datum should follow a real edge/corner in SolidCraft instead of remaining at a free local coordinate. AnchorTopology describes selection picks for an edge, adjacent face and optional endpoint.

mount = AnchorTopology(
    edge=(-20, 50, 5),
    on=(-20, 50, 10),
    corner=(-20, 0, 5),
)

Those coordinates are used to identify native topology. The intention is that SolidCraft keeps following that selected edge/corner when the underlying dimensions change.

Who should own an anchor?

An anchor belongs where its meaning originates:

ExampleOwner
A sensor connector position that is intrinsic to the sensorComponent
The top-left mounting datum of one particular frame assemblyAssembly
A generic rectangular face or cornerStandard Anchor

This prevents a generic component from accumulating project-specific names and offsets.

What should happen when dimensions change?

A good associative attachment is judged by its behaviour after an edit, not only by its initial picture. For example:

  1. a frame width changes from 800 to 900 mm;
  2. the semantic top-right corner moves;
  3. the child attached to that corner follows it;
  4. its local gap/offset still mean the same thing;
  5. no Python recompilation is needed for a saved-design parameter edit where the relationship is supported natively.

This is why Forge qualification cases explicitly edit saved SolidCraft parameters and measure the native result.

Current API boundaries

Forge currently supports standard rectangular anchors, named AnchorFrame values, topology-backed references and native rigid or planar attachment lowering for documented cases. It is not yet a general mate solver for arbitrary faces and every possible 3D relationship.

When we add a new attachment capability, its coordinate space and associativity must first be described here, then implemented and qualified in an isolated use scenario before it is used in a larger CAD project.
